# Action-order sensitivity of LLM planning in PDDL

This repository contains a controlled empirical study of **whether the textual order of PDDL action definitions affects the quality of plans generated by large language models**.

The core idea is deliberately narrow: the PDDL domain semantics stay fixed, while the order in which actions are presented to the model is changed. If plan quality changes under these semantically equivalent domain variants, then LLM planning is sensitive not only to the planning problem itself, but also to the surface structure of the symbolic specification.

## Abstract

Large language models are increasingly used as components in planning pipelines, but their behavior on formal planning inputs is not fully invariant to representation details. This project tests that problem in a generated `logistics` PDDL domain. For each planning problem, several semantically equivalent domain files are constructed by reordering the same action blocks. Multiple reasoning-oriented LLMs are then prompted to produce plans, and every produced plan is validated with VAL.

The experiment evaluates plan executability, goal reachability, conditional reachability, plan length, optimality ratio, token usage, and failure modes. Results are aggregated across repeated runs and tested statistically with paired tests and multiple-comparison correction.

## Research question

> Does the order of action definitions in a PDDL domain influence LLM planning performance when the underlying domain semantics are unchanged?

## Hypothesis

LLM-generated plans are expected to be sensitive to action ordering because the model receives the domain as a text sequence. Moving relevant actions toward the beginning, end, or dispersed positions of the prompt may change which operators are attended to, copied, or composed during plan generation.

## Experimental design

| Component | Description |
| --- | --- |
| Planning formalism | PDDL |
| Domain | Generated `logistics` domain |
| Task group | `alpha` |
| Problems | `p1`–`p20` |
| Repetitions | 15 runs per `(model, problem, order)` in the saved full experiment |
| Models | `deepseek/deepseek-v4-flash`, `gpt-oss-120b`, `nemotron-3-super` |
| Validator | VAL, called as `validate` |
| Baseline order | `canonical` |
| Main comparison unit | Paired `(problem, run)` samples within each model |

The full saved experiment contains 20 problems, 7 action-order variants, 15 runs, and 3 models, giving 6,300 validated model-output records for binary metrics.

## Action-order variants

Each variant preserves the same PDDL actions and changes only their textual order in the domain file.

| Variant | Definition |
| --- | --- |
| `canonical` | Original action order in the generated domain. |
| `disp_1` | Approximately one-third of the maximum Kendall-tau distance from `canonical`. |
| `disp_2` | Approximately two-thirds of the maximum Kendall-tau distance from `canonical`. |
| `disp_3` | Fully reversed canonical action order. |
| `plan_front` | Unique actions from the reference optimal plan are moved to the beginning in first-use order. |
| `plan_back` | Non-plan actions are placed first; reference-plan actions are placed at the end in reversed order. |
| `plan_scatter` | Reversed reference-plan actions are spread across the remaining non-plan actions. |

The `disp_*` variants are representation-level perturbations. The `plan_*` variants are diagnostic probes: they use the reference optimal plan to test whether the placement of useful actions changes model behavior.

## Pipeline

```text
PDDL domain + problem
        |
        v
Generate semantically equivalent action-order variants
        |
        v
Prompt LLM to output one PDDL action per line
        |
        v
Save raw response and extracted plan
        |
        v
Validate with VAL
        |
        v
Compute metrics, aggregate runs, build plots, run statistical tests
```

## Metrics

| Metric | Meaning |
| --- | --- |
| `parsable` | Whether strict VAL output avoids recognized parse-error patterns. This is a parse-quality signal, not proof of semantic correctness. |
| `executability` | 1 if VAL reports that the plan executed successfully or is valid; otherwise 0. |
| `reachability` | 1 if VAL reports `Plan valid`; otherwise 0. |
| `conditional_reachability` | Reachability among executable plans only; non-executable plans are excluded from the denominator. |
| `plan_length` | VAL plan length for parsable reachable plans; missing otherwise. |
| `optimality_ratio` | Validated plan cost divided by the reference optimal cost; defined only for reached goals. |
| `execution_progress` | Approximate progress before failure: parse errors are 0; state failures use `first_failure_step / (plan_length + 1)` when available. |
| `non_executable_failure` | 1 when validation records a parse error, state-execution error, or validator timeout. |
| Token metrics | Prompt, completion, reasoning, raw-completion, and total token usage normalized from provider payloads. |

## Statistical analysis

The reporting code uses the following tests:

- **Exact McNemar test** for paired binary metrics such as `reachability`, `executability`, and `non_executable_failure`.
- **Fisher's exact test** for `conditional_reachability`, because each order has its own executable-plan denominator.
- **Paired t-test** and **paired sign-flip permutation test** for numeric metrics.
- **Problem-level paired sign-flip tests** where runs are averaged inside each problem before testing across problems.
- **Bootstrap 95% confidence intervals** over problem-level differences.
- **Holm correction** inside each model/metric/test family.

This is intentionally more conservative than comparing unpaired aggregate means, because each order is matched by problem and run whenever possible.

## Current saved results

The generated reports are stored under `materials/logistics/graph/` and `materials/stats/`.

A few run-level observations from the saved experiment:

| Model | Canonical reachability | Notable order effect |
| --- | ---: | --- |
| `deepseek/deepseek-v4-flash` | 62.7% | `disp_3` drops reachability to 44.3%; exact McNemar Holm-adjusted p-value is below displayed precision. |
| `gpt-oss-120b` | 30.7% | `disp_3` drops reachability to 22.3%; exact McNemar Holm-adjusted p-value is 0.0093. |
| `nemotron-3-super` | 16.7% | `plan_front` raises reachability to 22.3%; exact McNemar Holm-adjusted p-value is 0.0200. |

These are empirical findings for the saved model/provider settings and generated logistics benchmark. They should not be read as universal claims about all LLMs or all PDDL domains.

## Reproducing the experiment

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

VAL must be available on `PATH` as `validate`.

For model runs, set an OpenRouter API key:

```bash
export OPENROUTER_API_KEY="your_key_here"
```

### 2. Generate domain variants

```bash
python3 main.py prepare --force
```

This creates the action-order variants for every configured problem.

### 3. Run model calls

Example: run one model on two problems and two orders.

```bash
python3 main.py models-run \
  --models deepseek/deepseek-v4-flash \
  --orders canonical disp_3 \
  --problems alpha p1 p2 \
  --runs 1
```

Example: run the full configured comparison for one model.

```bash
python3 main.py models-run \
  --models deepseek/deepseek-v4-flash \
  --orders canonical disp_1 disp_2 disp_3 plan_front plan_back plan_scatter \
  --problems alpha \
  --runs 15 \
  --jobs 5
```

### 4. Generate all graphs

```bash
venv/bin/python main.py graphs
```

This rebuilds `materials/logistics/graph/` from saved `llm_result.json` artifacts. It makes no model/API calls and does not change experiment results. The command creates both technical and Russian report versions of every aggregate and per-problem graph.

### 5. Build graphs and statistical reports

```bash
venv/bin/python main.py report
```

This runs the same graph generation and also rebuilds statistical-test files from saved artifacts.

## Methodological notes

- The experiment changes the **textual representation** of the PDDL domain, not the semantics of the actions.
- Validation is external to the LLM: generated plans are checked with VAL rather than accepted by string format alone.
- `plan_length` and `optimality_ratio` are computed only for plans that reach the goal, avoiding artificial zeros for failed plans.
- `plan_front`, `plan_back`, and `plan_scatter` are not intended as deployment strategies because they use reference optimal-plan information; they are controlled probes for studying representation sensitivity.
- Provider settings, quantization, and API-side model versions can affect results. The saved artifacts define the experiment actually analyzed here.

## Limitations

- The current benchmark uses one generated domain family (`logistics`). Additional domains are needed to test generality.
- The tested models are reasoning-oriented LLMs available through the configured provider stack; conclusions are limited to those settings.
- Some metrics are conditional on successful validation, so sample sizes differ across numeric summaries.
- The study measures plan generation from PDDL text, not natural-language-to-PDDL translation.
