# research_course_work

Minimal local pipeline for the generated `logistics` domain.

## Scope

- Domain: `logistics`
- Tasks: `alpha`
- Problems per task: `p1`-`p20`
- Models: `glm-4.7-flash` (`z-ai/glm-4.7-flash`), `mistral-small` (`mistralai/mistral-small-2603`), `gemma-4` (`google/gemma-4-26b-a4b-it`, provider `DeepInfra` with `fp8`), `google/gemma-4-31b-it` (provider `wandb` with `bf16`), `inclusionai/ling-2.6-flash`, `deepseek/deepseek-v4-flash` (provider `atlas-cloud` with `fp8`), `gpt-oss-120b` (`openai/gpt-oss-120b`, provider `DeepInfra` with `bf16`), `nemotron-3-super` (`nvidia/nemotron-3-super-120b-a12b:free`)
- Variants per problem:
  - `canonical`
  - `disp_1`
  - `disp_2`
  - `disp_3`
  - `plan_front`
  - `plan_back`
  - `plan_scatter`
- Problem labels use `sXX_lYY` naming, where `sXX` is the 1-based start action
  in the full plan and `lYY` is the optimal plan length.

## Requirements

- Python 3
- VAL on `PATH` as `validate`
- Prepared logistics materials under `materials/logistics`
- Packages from [requirements.txt](/Users/daniillickovaha/Documents/research/requirements.txt)

## Commands

Prepare base files and generate all variants:

```bash
python3 main.py --force
python3 main.py prepare
python3 main.py prepare --force
```

Run model jobs:

```bash
python3 main.py models-run --models glm-4.7-flash --orders canonical disp_3 --problems alpha p1 p2
python3 main.py models-run --models glm-4.7-flash mistral-small gemma-4 --orders canonical disp_1 disp_2 disp_3 --runs 5
python3 main.py models-run --models mistral-small gemma-4 --orders plan_front plan_scatter --problems alpha p1 p2 --runs 5
python3 main.py models-run --models gemma-4 --orders plan_front plan_scatter --runs 5 --start-run 6 --jobs 5
python3 main.py models-run --models inclusionai/ling-2.6-flash --orders canonical --problems alpha p1 --runs 1
python3 main.py models-run --models deepseek/deepseek-v4-flash --orders canonical --problems alpha p1 --runs 1
python3 main.py models-run --models google/gemma-4-31b-it --orders canonical --problems alpha p1 --runs 1
python3 main.py models-run --models gpt-oss-120b --orders canonical --problems alpha p1 --runs 1
python3 main.py models-run --models nemotron-3-super --orders canonical --problems alpha p1 --runs 1
python3 main.py models-run --models mistral-small --orders canonical --problems alpha p1 p5 p20 --runs 4 --force
```

In `--problems`, each task name scopes the following problem ids. A task without explicit ids selects all `p1`-`p20` for that task.

Build reports:

```bash
python3 main.py report
```

## Output layout

Each model run writes `llm_result.json`, `llm.plan`, and `run_status.json` under:

```text
materials/<domain>/<task>/<problem>/<variant>/<run>/<model_dir>/
```

Per-order aggregates are refreshed under:

```text
materials/<domain>/<task>/<problem>/<variant>/aggregate/<model_dir>.json
```

Reports are written to:

```text
materials/<domain>/graph/
├── alpha/
│   ├── p1/
│   └── ...
├── *_by_order_barplot.png
├── *_by_order_confidence_intervals.png
├── design/
└── confidence_intervals_by_order.csv
```

Per-problem barplots are generated by variant, with matching `*_confidence_intervals.png` point-range charts and `confidence_intervals.csv` tables in each problem folder. Top-level `*_by_order_barplot.png` files aggregate across all problems to compare the domain action orders (`canonical`, `disp_1`, `disp_2`, `disp_3`, `plan_front`, `plan_back`, `plan_scatter`), and top-level `*_by_order_confidence_intervals.png` files show the matching 95% confidence intervals. `plan_front` places unique optimal-plan actions at the beginning of the domain in first-use order. `plan_back` places all non-plan actions first, then the reversed optimal-plan actions. `plan_scatter` reverses those optimal-plan actions and spreads them across the remaining domain actions.
The `design/` folder contains presentation-ready versions of the top-level graphs with Russian order labels, shortened model labels, and a warmer visual style.

## Metric Semantics

The reports and statistical tests use the same analysis definitions:

- `parsable`: stored under `metrics.strict`; true when strict VAL output does not contain the currently recognized parse-error phrases. It is a parse-quality signal, not a guarantee that every object or action is semantically valid.
- `plan_length`: analysis length. If `parsable=true` and `reachability=true`, this is the strict VAL plan length from the saved log. If `parsable=false`, `reachability=false`, or validation metrics are missing, the value is missing and excluded from numeric summaries. For example, if only 2 of 15 runs reach the goal with lengths 10 and 12, the mean plan length is 11.
- `executability`: `1` when strict VAL reports that the plan executed successfully or is valid; otherwise `0`.
- `reachability`: `1` when strict VAL reports `Plan valid`; otherwise `0`.
- `conditional_reachability`: reachability among executable plans only. Non-executable plans are excluded from that metric's denominator.
- `optimality_ratio`: legacy VAL cost divided by the reference optimal cost; defined only for plans that reached the goal.
- `execution_progress`: strict validation progress. Parse errors are `0`; state-execution errors use `first_failure_step / (plan_length + 1)` when available; other strict outcomes with a known plan length are `1`.
- `first_failure_step`: first failed execution step parsed from strict VAL output; defined only for state-execution failures where VAL reports the step.
- `non_executable_failure`: `1` when strict validation records a parse error, state execution error, or validator timeout; otherwise `0`.
- Token metrics: `prompt_tokens`, `completion_tokens`, `reasoning_completion_tokens`, `raw_completion_tokens`, and `total_tokens` are normalized from the saved provider payload. Token breakdown plots use the reasoning/raw completion split, with `completion_token_breakdown_source` recording whether that split came directly from the provider or was estimated.
